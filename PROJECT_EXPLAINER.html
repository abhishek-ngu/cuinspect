1. What Is This Project?

One-sentence summary

A command-line tool that reads a compiled CUDA binary (.cubin or .elf), parses its ELF structure, extracts the embedded PTX source code and SASS microcode, and analyzes DWARF debug information to show kernel register usage, shared memory, and theoretical occupancy.

// Regex to find: .reg .b32 %r<32>;
std::regex reg32(R"(\.reg\s+\.b32\s+%r<(\d+)>)");
std::smatch match;
while (std::regex_search(ptx, match, reg32)) {
    maxReg = std::max(maxReg, std::stoi(match[1].str()));
}

// Find kernel entry points: .entry kernel_name(
std::regex entry(R"(\.entry\s+(\w+)\s*\()");

Step 4: Calculate theoretical occupancy

cpp
// SM limits for each architecture
struct SMLimits { int maxWarps, maxRegs, maxSharedKB, maxBlocks; };
static const map<int, SMLimits> limits = {
    {90,  {64, 65536, 228, 32}},  // H100: 64 warps, 64K regs, 228KB shared
    {80,  {64, 65536, 164, 32}},  // A100
};

// Limits:
// 1. Warps:    maxBlocks = maxWarps / warpsPerBlock
// 2. Regs:     maxBlocks = maxRegs / (regsPerThread * blockSize)
// 3. Shared:   maxBlocks = maxSharedKB*1024 / sharedMemPerBlock
// 4. Blocks:   maxBlocks = 32
// Occupancy = achievedWarps / maxWarps * 100%

5. Key Concepts You Must Be Able to Explain

ELF (Executable Linkable Format)

Standard binary format. CUDA binaries are ELF files with custom sections (.nv.*). Your tool uses LLVM's ELFObjectFileBase to parse them.

PTX (Parallel Thread Execution)

NVIDIA's intermediate assembly language. Virtual ISA — not executed directly. ptxas compiles it to SASS. Your tool extracts it from .nv.ptx section.

SASS

Actual GPU microcode (binary). What the GPU executes. In .nv.sass section. Not human-readable without nvdisasm.

DWARF

Debug info standard. CUDA extends it with NVPTX-specific operations: DW_OP_NVPTX_lane_id, DW_OP_NVPTX_warp_id, DW_OP_NVPTX_uniform.

Register Allocation

PTXAS assigns virtual registers (%r0-%r255) to physical registers. Spilling to local memory hurts performance. Your tool reads .reg .b32 %r; from PTX.

Occupancy

Ratio of active warps to max warps per SM. Limited by: registers, shared memory, block limit, warp limit. This is THE metric PTXAS optimizes for.

6. Likely Interview Questions & How to Answer

Q: "Walk me through what your tool does."

A: "It parses a CUDA ELF binary using LLVM's Object library. It enumerates sections, finds the GPU-specific ones (.nv.ptx, .nv.sass, .nv.info), extracts PTX source to analyze register usage and shared memory, calculates theoretical occupancy for the target architecture, and uses LLVM's DWARFContext to parse debug info and show variable locations with NVPTX-specific DWARF operations like lane_id and warp_id."

Q: "How do you calculate occupancy?"

A: "I look up the SM limits for the target compute capability (e.g., sm_90: 64 warps, 64K registers, 228KB shared). From PTX I get registers/thread and shared mem/block. I compute max blocks limited by each resource: warps, registers, shared memory, and block limit (32). The minimum gives achieved blocks × warps/block = achieved warps. Occupancy = achieved/max × 100%."

Q: "What's the difference between PTX and SASS?"

A: "PTX is a virtual ISA — stable across architectures, JIT-compilable. SASS is the actual microcode for a specific GPU. ptxas (the PTX assembler) does register allocation, instruction scheduling, barrier insertion, and emits SASS. My tool finds both in the ELF: .nv.ptx (text) and .nv.sass (binary)."

Q: "What are NVPTX DWARF extensions?"

A: "Standard DWARF assumes a single thread of execution. GPU has 32 threads/warp. NVPTX extensions add: DW_OP_NVPTX_lane_id (thread index in warp), DW_OP_NVPTX_warp_id, DW_OP_NVPTX_smid, DW_OP_NVPTX_uniform (value same across warp), DW_OP_NVPTX_divergent. My tool parses these to show which variables are uniform vs divergent."

Q: "Why use LLVM's Object library instead of writing your own ELF parser?"

A: "LLVM's Object library is production-grade, handles ELF32/64, endianness, section types, relocations, and integrates with DWARFContext. It's what NVIDIA's own tooling (llvm-objdump, lld) uses. Re-inventing it would be error-prone and miss edge cases."

Q: "How would you extend this to show SASS instruction mix?"

A: "Parse .nv.sass section, pipe to nvdisasm (or use LLVM's MCDisassembler for NVPTX), categorize instructions: FMA/ALU, LD/ST, CTRL, TEX, SYNC. Show percentage per category — this reveals if kernel is memory-bound or compute-bound."
